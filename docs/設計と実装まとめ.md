# スコアサーバー 設計・実装まとめ

A&D（Attack & Defense）形式 CTF 向けのスコアサーバー。
ForcAD のフラグ受付・スコア計算ロジックを **FastAPI + SQLAlchemy(async)** に移植し、
スコア表示は **CTFd の AWD プラグイン**を流用する構成。

> 担当範囲: **スコア計算・フラグ受付**
> 別チーム担当: フラグローテーター（`engineering-design-5th-grade`）・SLA チェッカー

---

## 1. システム全体構成

```
[別チーム]                          [本リポジトリ: score-server]              [CTFd]

フラグローテーター ──書込──▶  MySQL(ctf_flags)
(SSH配布 + DB書込)                  │  flags(round,team,service,flag)
                                    │
                                    ▼  ポーリング取込 (5秒間隔)
                            ┌──────────────────────┐
参加チームPC ──PUT /flags/──▶│   Score Server        │
(X-Team-Token)              │   (FastAPI)           │── PUT /plugins/awd/api/update ──▶ CTFd
                            │                       │   (host.docker.internal:8000)    スコアボード表示
SLAチェッカー ──POST /sla──▶│   PostgreSQL          │
(X-Internal-Key)            │   Redis (cache)       │
                            └──────────────────────┘
```

**3 つの連携経路:**

1. **ローテーター → score-server**: ローテーターが MySQL `ctf_flags.flags` に直接書き込み、score-server がポーリングして PostgreSQL に取り込む。
2. **参加チーム → score-server**: `PUT /flags/` でフラグ提出（攻撃）。
3. **score-server → CTFd**: ラウンド切り替え時に集計を AWD プラグインへ POST し、CTFd のスコアボードに反映。

## 3. データフロー詳細

### 3-1. フラグ取り込み（ローテーター → score-server）

ローテーターは設計上、新フラグを各チーム VM へ SSH 配布すると同時に、
スコアサーバー上の MySQL `ctf_flags.flags` テーブルへ直接書き込む。

score-server は HTTP 受信ではなく **MySQL ポーリング**で取り込む（[app/services/ingest.py](../app/services/ingest.py)）:

1. `INGEST_POLL_SECONDS`（既定 5 秒）ごとに `MAX(round)` を確認
2. `current_round` より新しいラウンドのフラグ行を読む
3. **team/service の「名前」を内部 ID に解決**（ローテーターは team_id/service_id を持たず名前で扱う）
4. `flags` / `team_services` に INSERT、Redis にキャッシュ
5. 直前ラウンドの集計を CTFd へ反映し、`current_round` を進める

> **名前マッピング**: `teams.name` / `services.name` をローテーター `config.py` の
> `TEAMS[].name` / `services` キーと一致させる必要がある（`team1` / `service-a` / `service-b`）。
> 不一致は警告ログを出してスキップ。

### 3-2. フラグ提出（攻撃）

`PUT /flags/`（`X-Team-Token` 認証）で受け付け、ForcAD の判定順序を踏襲:

1. フラグ取得（Redis 優先、無ければ DB）→ 無効なら reject
2. 自チームのフラグ → reject
3. 有効期限切れ（`current_round - flag.round > flag_lifetime`）→ reject
4. `volga_attacks_mode` 時、自サービス DOWN なら reject
5. PostgreSQL ストアド関数 `handle_flag_stolen()` でアトミックに加点

**二重提出防止**は `stolen_flags` の複合主キー `(flag_id, attacker_id)` で DB レベル保証。

### 3-3. CTFd 反映

ラウンド切り替え時、直前ラウンドの集計を `/plugins/awd/api/update` へ POST（[app/services/ctfd.py](../app/services/ctfd.py)）:

```json
{ "id": <challenge_id>, "token": "<token>",
  "attacks": {"<ctfd_team_id>": <points>}, "defenses": [<ctfd_team_id>, ...] }
```

CTFd 側は Awards テーブルに `[AWD] Attack` / `[AWD] Defense` として記録し、自動集計してスコアボード表示する。
**CTFd 連携は下流のベストエフォート**であり、失敗してもフラグ取り込み・スコア計算は止めない設計。

## 4. データベーススキーマ（PostgreSQL）

| テーブル | 役割 |
|---|---|
| `game_config` | ゲーム設定（flag_lifetime, round_time, defense_point, volga_attacks_mode） |
| `teams` | チーム（name, ip, token, **ctfd_team_id**） |
| `services` | サービス（name, flag_prefix, **ctfd_challenge_id**, **ctfd_token**） |
| `flags` | フラグ（flag, team_id, service_id, round, expires_at） |
| `stolen_flags` | 奪取済みフラグ（複合PK で二重提出防止） |
| `team_services` | ラウンド別集計（stolen, lost, attack_pts, defense_pts, sla_status, checks…） |
| `sla_results` | SLA チェック結果の記録 |

`ctfd_team_id` / `ctfd_challenge_id` / `ctfd_token` は ForcAD には無い、CTFd 連携用の追加カラム。

## 5. API エンドポイント

| メソッド・パス | 呼び出し元 | 認証 | 説明 |
|---|---|---|---|
| `PUT /flags/` | 参加チームPC | `X-Team-Token` | フラグ提出（攻撃） |
| `POST /sla` | SLA チェッカー | `X-Internal-Key` | SLA 結果受け取り |
| `GET /scoreboard` | 公開 | なし | スコア一覧（運営/デバッグ用 JSON） |
| `GET /attack_data` | 参加チームPC | `X-Team-Token` | 攻撃ヒント（public_flag_data） |
| `GET /health/` | 監視 | なし | DB/Redis 稼働確認 |

> フラグ取り込みは HTTP ではなくローテーター MySQL のポーリングで行うため、`/flags/rotate` は廃止。
> 参加者が見るスコアボードは **CTFd 側**を流用し、`/scoreboard` は運営用 JSON API。

## 6. 起動・運用手順

### 6-1. 起動

```bash
cd score-server
docker compose up --build
```

起動時に `scripts/init_db.py` がスキーマ・ストアド関数・seed データを投入する。
`flagdb`（MySQL）はローテーターが `localhost:3306` で書き込む先。

### 6-2. 実構成への調整

[scripts/seed.py](../scripts/seed.py) を編集して `python -m scripts.init_db` を再実行するだけ:

- `TEAMS` … name はローテーター `config.py` と一致必須。`ctfd_team_id` は CTFd のチームID
- `SERVICES` … name はローテーターの service キーと一致必須。`ctfd_challenge_id` / `ctfd_token` は CTFd の AWDChallenge の値

### 6-3. CTFd 側の準備

1. CTFd を Teams モードでセットアップ
2. **AWD プラグイン**を `CTFd/plugins/awd/` に配置（後述のトラブル参照）
3. チームと AWDChallenge を作成し、`id` / 自動生成 `token` を seed.py に反映
4. CTF を開始状態にする（AWD 更新は開始中のみ受理）

### 6-4. 主な環境変数

| 変数 | 既定値 | 説明 |
|---|---|---|
| `DATABASE_URL` | `postgresql+asyncpg://score:score@db:5432/score` | PostgreSQL |
| `REDIS_URL` | `redis://redis:6379/0` | Redis |
| `ROTATOR_DATABASE_URL` | `mysql+aiomysql://rotator:Rotator1!@flagdb:3306/ctf_flags` | ローテーターMySQL |
| `CTFD_URL` | `http://host.docker.internal:8000` | CTFd（別compose のためホスト経由） |
| `INGEST_POLL_SECONDS` | `5` | 取り込みポーリング間隔 |
| `INTERNAL_KEY` | `change-me-internal-key` | SLA/内部API 共有シークレット |
| `LOG_LEVEL` | `info` | ログレベル |

## 7. 移植元・連携先の対応

| 機能 | 出典 | 変更点 |
|---|---|---|
| フラグ判定順序 | ForcAD `attacks.py handle_attack()` | FastAPI + async 化 |
| Redis キー体系 | ForcAD `storage/keys.py` | そのまま移植 |
| DB スキーマ | ForcAD `create_tables.sql` | CTFd 連携カラム追加 |
| ストアド関数 | ForcAD `recalculate_rating()` | Elo廃止、単純加算に変更 |
| TaskStatus Enum | ForcAD `types.py` | そのまま移植 |
| フラグ取り込み | （新規） | ローテーターMySQLのポーリング方式 |
| CTFd スコア書込 | CTFd `plugins/awd awd_update()` | httpx で POST |

## 8. これまでに解決した問題（トラブルシュート記録）

| 事象 | 原因 | 対処 |
|---|---|---|
| `cannot insert multiple commands into a prepared statement` | asyncpg は複数文を prepared statement で実行不可 | SQL 投入を生コネクションの simple query protocol に変更 |
| `cryptography package is required` | MySQL8 の `caching_sha2_password` 認証に必要 | `cryptography` を requirements に追加 |
| `ping() missing argument 'reconnect'` | aiomysql と `pool_pre_ping` の非互換 | ローテーターエンジンの `pool_pre_ping` を無効化 |
| `Table 'ctf_flags.flags' doesn't exist` | ローテーター未起動でテーブル未作成 | 起動時/各ポールで `CREATE TABLE IF NOT EXISTS`（同一スキーマ） |
| CTFd ダッシュボードが開けない | Docker Desktop 停止 + AWD プラグインが `path/to/...` の仮パスに誤配置 | プラグインを `CTFd/plugins/awd/` へ配置し再起動 |
| ローテーターが flagdb に繋がらない | flagdb のホストポートを 3307 にしたため 3306 と不一致 | flagdb を 3306 に戻す（競合 mariadb を停止） |
| CTFd push 失敗で取り込みが停止 | push の例外が取り込みループ全体を巻き込み | push をベストエフォート化（例外を握ってログ）+ `host.docker.internal` 経由に変更 |

---

## 9. 検証済みの連携状態

- **ローテーター → flagdb(MySQL:3306)**: ローテーター本体の `db.py` で書込成功
- **flagdb → score-server(PostgreSQL)**: 新ラウンドのフラグを取り込み、名前→ID 解決も動作
- **score-server → CTFd**: `host.docker.internal:8000` 経由で到達（HTTP 200）

## 10. 残課題

- CTFd 側のチーム・AWDChallenge を本番構成分そろえ、`seed.py` に ID/token を反映する運用フローの確定
- 攻撃の E2E 確認には 2 チーム以上が必要（フラグ提出 → attack_pts 加算）
- 防御ポイント計算ルールの最終確定（現状: SLA UP かつ そのラウンドで未奪取なら付与）
